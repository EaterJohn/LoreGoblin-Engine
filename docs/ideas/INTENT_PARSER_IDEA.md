## 1. Суть в двух строках

Ввод игрока разбирается **без LLM**: слова сопоставляются с лексиконом, который
берётся из данных мира (имена, алиасы, теги заклинаний/предметов/NPC).
Разбор идёт последовательными проходами, и каждый проход сужает набор
допустимого: намерение → состояние → метод → цель → исполнение.

LLM остаётся интерфейсом и рассказчиком: описывает результат игроку, а если
команда сработала неверно или не сработала, видит структурированную ошибку
и может помочь игроку (переспросить, объяснить).

## 2. Зачем

- **Дёшево и быстро:** обычные ходы не тратят токены и время инференса.
- **Воспроизводимо и тестируемо:** «фраза → ожидаемый кадр намерения» это
  обычный юнит-тест. LLM-парсер так не проверишь.
- **Подходит слабой модели** (Gemma e4b): ей не нужно выбирать тулы и
  аргументы, ошибки выбора тула (класс бага из #ENG-012) исключаются.
- **Не даёт модели «подбирать формулировку», пока движок не пропустит**:
  исход решает Engine по правилам, а не согласие модели.
- Продолжает принципы проекта: Engine знает, что существует; LLM не
  источник истины (#ENG-001).

## 3. Как это работает

### 3.1 Пример

Фраза игрока: «Атакую, я бросаю фаербол в того мага».

```text
0. Токенизация + лемматизация фразы (один раз).
1. Проход НАМЕРЕНИЯ:   "атакую"            -> категория ATTACK
   Автомат состояний:  EXPLORATION -> COMBAT (если предусловия выполнены)
2. Проход МЕТОДА (внутри состояния COMBAT, допустимы только боевые действия):
                       "бросаю фаербол"    -> способность fireball
                       (теги: fire, projectile; алиасы: огненный шар, шар огня)
3. Проход ЦЕЛИ:        "того мага"         -> кандидаты в бою с тегом/типом mage
                       если один -> цель; если несколько -> вопрос игроку
4. Проверка полноты:   есть способность? цель допустима? ресурсы есть?
5. Исполнение:         Engine бросает/считает попадание, применяет последствия
6. Результат (структура) -> LLM-рассказчик описывает игроку
```

### 3.2 Проходы потребляют токены одного разбора

Фраза разбирается **один раз**, а проходы «забирают» свои токены
(«атакую», «бросаю фаербол», «мага»). Непотреблённое («того») идёт
подсказкой следующему проходу. Это сохраняет последовательность
«намерение → состояние → метод → цель», но не теряет информацию из
исходной фразы.

### 3.3 Автомат состояний как фильтр

Состояние определяет допустимые действия. Это работает как фильтр
неоднозначности: тег `fire` есть у заклинания, факела и дыхания дракона,
но в состоянии COMBAT остаются только боевые действия.

Автомат описывает **режимы игры** (исследование, диалог, торговля, бой),
а не логику каждого объекта. Торговая сессия из #ENG-019 уже является
первым таким режимом.

### 3.4 Уверенность и запасные пути

Каждый проход возвращает кандидатов с оценкой уверенности.

| Ситуация | Действие |
|---|---|
| один уверенный кандидат | исполнить |
| несколько близких | нумерованный вопрос игроку (как в торговле, #ENG-019) |
| ничего не подошло | «не понял» + запись фразы в лог непонятого |
| низкая уверенность (опционально) | запасной вызов LLM: выбрать **из списка допустимых кандидатов**, не генерировать свободно |

### 3.5 Три исхода, которые нельзя смешивать

- **Невалидно** (не разобралось, неоднозначно): переспросить или запасной путь.
- **Запрещено правилами:** это не ошибка, рассказчик описывает отказ,
  переформулировать и пробовать снова нельзя.
- **Не удалось** (бросок, порог): обычный исход, тоже нарратив.

## 4. Что нужно для реализации

1. **Формат лексикона в данных мира.** У способностей, предметов, NPC:
   базовые имена, алиасы, теги. Авторы пишут только базовые формы.
2. **Лемматизация русского** (кандидат: `pymorphy3`; проверить актуальность)
   и нечёткое сравнение для опечаток (кандидат: `rapidfuzz`; проверить).
3. **Кадр намерения** (структура): `verb/category`, `method`, `target`,
   `modifiers`, `confidence`, `unconsumed_tokens`.
4. **Автомат состояний:** словарь «состояние → допустимые категории
   действий → переходы». Контекст: последняя цель, последнее действие.
5. **Правила против ложных срабатываний:** отрицание («не бросаю»),
   вопрос/гипотеза («а что если кину…»), ссылки («его», «того», «ещё раз»).
6. **Разбор нескольких действий** в одной фразе («сначала… потом…»):
   отдельная подзадача, можно отложить.
7. **Лог непонятого** и файл «золотых фраз» (фраза → ожидаемый кадр) как
   тесты и как сырьё для роста лексикона.

## 5. Известные трудности

- **Русская морфология и синонимия** это главная скрытая стоимость. Архитектура
  простая, покрытие живой речи растёт постепенно.
- Игроки пишут свободно и длинно; часть ввода всё равно придётся отдавать
  запасному пути.
- Формат лексикона должен быть удобен модерам: это часть публичного
  контракта world pack.
- Автомат не должен разрастаться: режимов игры немного, поведение NPC
  моделируется отдельно (behavior trees / utility AI, если понадобится).

## 6. Роль LLM

- Рассказчик: описывает структурный результат Engine.
- Ассистент: видит структурную ошибку (`ok:false`, код, причина), может
  переспросить игрока или пояснить.
- Запасной выбор при низкой уверенности, только из списка кандидатов.
- На этапе создания мира: предлагать алиасы и теги для новых сущностей,
  автор просматривает результат.

## 7. Аналоги, у которых можно подсмотреть

| Что | Чем полезно |
|---|---|
| Парсеры интерактивной литературы: Infocom, Inform 7, TADS | Классика детерминированного разбора глагол + объекты, работа с неоднозначностью и уточняющими вопросами |
| Evennia (Python-фреймворк MUD) | Наборы команд, зависящие от контекста (cmdsets), близко к состояниям автомата |
| Task-oriented dialogue: intent + slot filling, dialogue state tracking | Терминология и паттерны для «намерение → параметры → состояние» |
| Каскадный NLU (дешёвый разбор первым, дорогой запасным) | Схема «правила → запасной LLM» |
| RealmAI Engine (открытый проект, найден при обзоре) | Близкая цель (детерминированный движок + LLM-рассказчик), но разбор фраз там делает маленькая LLM-модель, а не правила. Полезно как контраст и для идеи разделения интерпретатора и рассказчика |

Оговорка: сведения об этих проектах и библиотеках получены из обзора и
памяти, перед использованием проверять актуальное состояние.

## 8. Связь с существующими решениями

- #ENG-013/014: детерминированная фильтрация тулов вместо discovery; автомат
  состояний её естественное развитие.
- #ENG-019: контекстная торговая сессия = первое состояние автомата.
- #ENG-022: контракт «call() не бросает»; кадр намерения должен
  возвращать структурные ошибки в том же формате.
- #ENG-017: нарратор не имеет права считать `ok:false` выполненным; в этой
  схеме рассказчик получает только структурный результат.
- #ENG-003: лог непонятого и события Engine могут питать память/суммаризацию.

## 9. Оценка сложности (грубо)

- Минимальный прототип: 3–4 глагола, лемматизация, лексикон из `world.json`,
  автомат из двух состояний, один вопрос-уточнение: **дни**.
- Надёжное покрытие живой русской речи: **постепенно**, ограничено размером
  лексикона и набора тестовых фраз, а не архитектурой.

## 10. Открытые вопросы

- Формат лексикона в `world.json` (где хранить алиасы и теги, как
  версионировать).
- Нужен ли запасной вызов LLM на первом этапе или сначала чистые правила.
- Как представлять кадр намерения и где он живёт (`engine/` или отдельный
  слой, не знающий конкретных миров).
- Разбор нескольких действий в одной фразе: когда и как.
- Порог уверенности: как выбирать и как измерять.

## 12. Дополнения (из сводных заметок, 2026-09-30)

- **Цепочка действий слева направо.** Фраза «атакую, потом отступаю» разбивается на
  действия, которые выполняются по одному, с проверкой состояния между ними
  (очередь действий).
- **Слоистая проверка состояний:** можно ли войти в действие сейчас (в диалоге
  нельзя атаковать, без ресурса нельзя применить способность).
- **Классы прерываний как данные world pack:** мягкие (торговля, диалог, осмотр,
  прерываются любым действием), жёсткие (бой, падение, смерть, прерываются только
  заданными событиями), атомарные (удар, шаг, не прерываются). Подробности:
  `AFFORDANCES_AND_PERSISTENCE_IDEA.md`, раздел 5.
- **Язык ввода — параметр мода** (`locale`), а не константа движка; лексикон парсера это данные мода. Ввод на языке, которого нет в лексиконе мира, получает отказ (решение владельца проекта, 2026-10-01; кандидат в `DECISIONS.md`, см. `IDEAS_INDEX.md`).
- **Отказ лучше ошибки:** действие, которого нет в схеме или нет в этом
  состоянии, даёт `{action: "unknown"}` и понятный отказ («ты не можешь этого
  сделать в данной ситуации»). Реплики вида «я бог» не становятся фактами:
  игрок действует, а не объявляет реальность.
- **Допустимый список для разбора** это аффордансы объектов в текущем состоянии
  (закрытый мир), см. `AFFORDANCES_AND_PERSISTENCE_IDEA.md`.
- **Для нестандартных творческих цепочек** («залью водой, заморожу, ударю молотом»)
  возможна роль LLM как планировщика атомарных шагов из словаря Engine, при этом
  каждый шаг разрешает Engine (там же, раздел 6).
- **Общий лексикон** используется и парсером, и проверкой нарратива
  (`EVENTS_AND_KNOWLEDGE_IDEA.md`, раздел 8).
