## Слои системы

```text
PLAYER
  ↓
LLM (llm/ollama.py)
  — понимает намерение игрока
  — ведёт диалог, думает за NPC, рассказывает сцену
  — НЕ хранит и НЕ придумывает канон
  ↓ tool calls
ENGINE (engine/)
  — правила мира: экономика, инвентарь, статы, время
  — единственное место, где меняется состояние мира
  ↓
SQLite (data/worlds/<world>/world.db)
  — источник истины (source of truth)
```

Правило прохождения данных: LLM никогда не пишет в SQLite напрямую и
никогда не считает утверждение игрока фактом без подтверждения тулом.
Реализовано через системный промпт + tool-calling; проверено тестом
"легендарный меч, которого нет в таверне" (пройден).

## Модули и их ответственность

| Модуль | Отвечает за | НЕ должен |
|---|---|---|
| `engine/database.py` | SQL-схема, соединение, низкоуровневые query/execute | знать о конкретных сущностях мира |
| `engine/world.py` | Игровая механика: покупка, статы, время, поиск сущностей, загрузка world data | знать конкретные сущности мира |
| `engine/actions.py` | Описание tools для LLM (JSON-schema) + роутинг вызова к `WorldEngine` | содержать игровую логику — только маппинг имя→метод |
| `llm/ollama.py` | HTTP-клиент к Ollama API, ничего больше | принимать решения об игровом мире |
| `main.py` | Цикл диалога, сборка system prompt, REPL-команды (`/state` и т.д.) | содержать бизнес-логику мира |
| `data/worlds/<name>/` | Весь лор конкретного мира: сущности, стартовое состояние, system prompt-надстройка | — (это данные, не код) |

## Принцип: движок world-agnostic, миры — это данные

Целевая (частично не реализованная) схема:

```text
data/worlds/
  allizium/
    world.json          # стартовые entities, world_state, money
    system_prompt.txt    # надстройка к общему system prompt движка
    world.db             # генерируется при первом запуске, в .gitignore
  <любой другой мир>/
    world.json
    system_prompt.txt
```

`engine/world.py` должен получить метод `load_world(path)`, читающий
`world.json` и делающий те же INSERT'ы, что сейчас хардкодит
`seed_demo_world()`. После рефакторинга `seed_demo_world()` станет тонкой
обёрткой `load_world('data/worlds/allizium/world.json')` — см.
`DECISIONS.md` #ENG-004 для статуса.

Система статов (STR/CON/DEX...) уже сейчас не зашита в код — она часть
`data` игрока в seed-данных, `upgrade_stat` читает набор статов динамически.
Значит, движок уже умеет работать с произвольным набором характеристик,
если они заданы в данных мира — это не требует правок под другой сеттинг.

## Слои знания (спроектировано, не реализовано)

Для защиты от дрейфа контекста на длинной дистанции запланировано пять
категорий:

- **CANON** — то, что реально существует (SQLite: `entities`, `world_state`, `events`).
- **KNOWN** — что конкретный NPC/игрок знает (подмножество CANON).
- **INFERENCE** — что можно предположить, но не подтверждено.
- **PLAYER CLAIM** — что сказал игрок (не факт, пока не подтверждён CANON).
- **NARRATION** — что рассказала LLM (стиль/подача, не источник истины).

Ключевое правило: `PLAYER CLAIM ≠ CANON`. Реализовано частично — через
tool-calling проверку перед описанием сцены; отдельных таблиц/полей под
KNOWN/INFERENCE ещё нет.

## Долгая память диалога (спроектировано, не реализовано)

Открытая проблема — `messages` в `main.py` живёт только в оперативной
памяти процесса и не персистится. Согласованный план (см. `DECISIONS.md`
#ENG-003):

1. Персистентность истории сообщений в SQLite.
2. Sliding window (последние N ходов как есть) + rolling summary
   (более старые ходы сжимаются отдельным изолированным вызовом LLM,
   не тем же контекстом, где идёт RP).
3. Summary — не источник истины (в отличие от CANON), допускает
   неточности, потому что факты всё равно проверяются через Engine
   при каждом запросе.

## Что специально НЕ делаем сейчас

- Не пытаемся сразу построить полный мир/генератор/боёвку/магию —
  см. принцип "вертикальный срез, потом расширение маленькими
  проверяемыми шагами".
- Не размазываем систему статов/валюты по коду движка — если мир не
  использует "серебро" как валюту, менять схему `money` рано, но
  название колонки `silver` в `database.py` — известное лор-протекание,
  зафиксировано как техдолг, не блокер.
