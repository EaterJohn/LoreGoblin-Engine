## #ENG-001 — Базовая архитектура: Engine как источник истины
- Дата: 2026-09-27
- Кем: пользователь
- Статус: Реализовано
- Решение: LLM не читает и не придумывает мир напрямую — только запрашивает
  состояние через Engine. Разделение: Engine = физика и бухгалтерия мира,
  LLM = мозг NPC + интерпретатор намерений + рассказчик.
- Почему: без этого разделения LLM неизбежно "плывёт" на длинной дистанции
  (тысячи ходов) — то, что мы называем дрейфом канона.

## #ENG-002 — Tool-call loop должен быть многораундовым
- Дата: 2026-09-28
- Кем: ИИ (аудит кода), патч — ИИ
- Статус: **Реализовано**
- Проблема: в `main.py` после получения результатов тулов делался только
  один повторный вызов `llm.chat()`. Если модель после этого снова хотела
  вызвать тул — второй вызов не обрабатывался, потому что не было цикла
  `while calls:`.
- Решение: вынесен `run_tool_loop(llm, api, messages)` в `main.py` — цикл
  до `MAX_TOOL_ROUNDS=8` раундов (защита от зацикленного tool-call, не
  просто бесконечный `while`). Возвращает финальный текст, либо явное
  сообщение о превышении лимита раундов.

## #ENG-002b — Обработка ошибок связи с Ollama
- Дата: 2026-09-28
- Кем: ИИ
- Статус: Реализовано
- Проблема: `llm/ollama.py` не ловил сетевые ошибки — при недоступной
  Ollama всё приложение падало трейсбэком `urllib`.
- Решение: `OllamaClient.chat()` ловит `urllib.error.URLError` и
  `json.JSONDecodeError`, поднимает понятный `RuntimeError`.
  `run_tool_loop` в `main.py` перехватывает его и возвращает игроку
  читаемое сообщение вместо падения процесса.

## #ENG-003 — Персистентность диалога и суммаризация
- Дата: 2026-09-28
- Кем: ИИ (предложение по итогам обсуждения)
- Статус: Направление обсуждено, финальное решение отложено — пользователь
  собирается принести собственные наработки по суммаризации из другого
  проекта, адаптация будет отдельным решением после этого.
- Проблема: `messages` в `main.py` существует только в памяти процесса,
  не сохраняется между запусками; без ограничения роста рано или поздно
  либо обрежется контекстным окном модели, либо начнёт терять начало.
- Предложенное направление:
  1. Писать историю сообщений в SQLite, чтобы диалог переживал перезапуск.
  2. Sliding window (последние N ходов как есть) + rolling summary более
     старых ходов.
  3. Суммаризация — **отдельный изолированный вызов LLM**, не тот же
     контекст, где идёт RP (разная нужная temperature, разная роль,
     риск утечки нарративного стиля в сухую фиксацию фактов).
  4. Summary — narrative-context, не CANON: неточности в нём менее
     опасны, потому что факты (деньги, инвентарь) всё равно проверяются
     через Engine при каждом запросе, а не берутся из summary.

## #ENG-004 — Ядро движка должно быть world-agnostic
- Дата: 2026-09-28
- Кем: пользователь (заказал требование — движок не только под мир
  Allizium, рассчитан на модинг/opensource), ИИ (предложил конкретную
  реализацию)
- Статус: Решено как направление, реализация не начата
- Проблема: весь демо-мир (Иван, Борис, таверна «Красный Факел»,
  предметы) захардкожен в `engine/world.py::seed_demo_world()`.
  Дополнительно: дефолтный параметр `seller_id='boris'` продублирован в
  `world.py` и `actions.py`.
- Решение: вынести весь лор в `data/worlds/<name>/world.json` +
  `system_prompt.txt`. Добавить в `WorldEngine` generic-метод
  `load_world(path)`. `seed_demo_world()` станет тонкой обёрткой
  `load_world('data/worlds/allizium/world.json')`. Убрать дефолт
  `seller_id='boris'`, сделать параметр обязательным. System prompt
  разделить на движковую часть (общие правила, одна на все миры) и
  мир-специфичную надстройку (тон, атмосфера конкретного сеттинга).
- Уточнение: система статов (STR/CON/DEX...) уже была устроена
  правильно — она часть `data` игрока в seed-данных, а не код движка,
  переделывать не требуется.

## #ENG-009 — Стратегия многокарточного/многомашинного инференса
- Дата: 2026-09-28
- Кем: ИИ (рекомендация)
- Статус: Рекомендовано, не подтверждено пользователем как принятое к
  действию
- Контекст: три ПК с RTX 2060 Super (8 ГБ), RTX 4060 (8 ГБ), RTX 5060
  (16 ГБ).
- Решение: для текущей маленькой модели (Gemma e4b) — клиент-серверная
  схема: Ollama поднимается на самом мощном ПК с `OLLAMA_HOST=0.0.0.0`,
  остальные ПК обращаются к нему по сети через уже существующий параметр
  `host` в `OllamaClient`. Разбиение модели по нескольким машинам через
  `llama.cpp --rpc` — резерв на случай, если понадобится модель, которая
  физически не влезает ни в одну из трёх карт по отдельности (ориентир —
  30B+ параметров); для модели, которая и так помещается на одной карте,
  сетевое разбиение обычно замедляет генерацию, а не ускоряет её.
  Дополнительно: Ollama не поддерживает `--rpc`, для RPC-кластера
  потребуется отдельно `llama-server` с OpenAI-совместимым API вместо
  `/api/chat`.

## #ENG-011 — Манифест/lock-файл модов как CANON, диаграммы как NARRATION
- Дата: 2026-09-28
- Кем: пользователь (предложил идею "диаграмма проекта + версионирование
  модов"), ИИ (развёл на два слоя и предложил конкретный формат)
- Статус: Решено как направление, реализация (генератор диаграмм,
  установщик модов) не начата
- Решение: зависимости модов описываются машиночитаемо —
  `manifest.json` на мод (id, version, requires_engine, depends_on,
  provides) + `installed_mods.lock.json` на сборку (фактически
  разрешённое состояние). Это источник истины. Mermaid-диаграммы —
  производная, генерируются по запросу из этих данных, никогда не
  хранятся и не редактируются как отдельный файл состояния. При большом
  числе модов диаграмма строится не целиком, а как отфильтрованный
  подграф вокруг конкретного узла (глубина 1–2), чтобы оставаться
  читаемой.
- Почему: тот же принцип, что уже в основе движка (`ENG-001`,
  `ENG-004`) — источник истины должен быть один и машиночитаемый, а
  визуализация — производная и одноразовая, иначе неизбежен дрейф между
  "что нарисовано" и "что реально установлено". Формат сознательно
  повторяет проверенный паттерн lock-файлов пакетных менеджеров
  (npm/Cargo), а не изобретается с нуля.
- Подробности: `docs/MODDING.md` (раздел про манифест и lock-файл),
  `docs/DEPENDENCY_GRAPH.md` (правила генерации диаграмм, черновой
  контракт генератора).

## #ENG-012 — Баг: `get_inventory` неверно отвечал на "что продаёт NPC"
- Дата: 2026-09-28
- Кем: пользователь (поймал живьём в реальном логе диалога с Gemma), ИИ (диагностика и патч)
- Статус: Реализовано
- Проблема: в живом прогоне игрок спросил Бориса "что вы продаёте", Gemma
  честно вызвала `get_inventory(owner_id='boris')`, получила пустой
  инвентарь и сообщила, что Борису нечего продать. Это неверно: правило
  `buy_item` определяет товар продавца через co-location (предмет с ценой
  в той же локации), а не через таблицу `inventory` (та хранит только уже
  купленные вещи). Модель использовала Engine правильно по форме, но
  выбрала семантически близкий, а не корректный тул — итог противоречил
  собственной логике движка, что опаснее прямой выдумки, потому что
  выглядит обоснованным.
- Решение: добавлен `WorldEngine.get_seller_stock(seller_id)` — возвращает
  ровно то же множество товаров, которое `buy_item` считает покупаемым у
  этого продавца (та же co-location-логика). Покрыто тестом
  `test_seller_stock_matches_buy_item`, который явно проверяет, что всё
  перечисленное `get_seller_stock` реально проходит через `buy_item`.

## #ENG-013 — Контекстная фильтрация tools + шпаргалка в system prompt
- Дата: 2026-09-28
- Кем: пользователь (поднял вопрос про help-систему для слабой модели), ИИ (предложил альтернативу)
- Статус: Реализовано
- Контекст: на модели с маленьким контекстным окном (~16k) нельзя
  рассчитывать на сложное многоступенчатое рассуждение по выбору тула.
  Обсуждалась idea "help-команда с категориями" — отклонена (см. #ENG-014)
  в пользу двух более дешёвых механизмов.
- Решение:
  1. `ActionAPI.tools(location_id=None)` — торговые тулы (`buy_item`,
     `get_seller_stock`) попадают в список, только если
     `WorldEngine.location_has_shop(location_id)` истинно (в локации есть
     хотя бы один NPC и хотя бы один предмет с ценой). Фильтрация
     происходит в Python до того, как модель увидит список — не требует
     от модели никакого рассуждения. `location_id=None` (как в отладочной
     команде `/tools`) — безопасный дефолт, полный список.
  2. `run_tool_loop` в `main.py` запрашивает текущую локацию игрока на
     каждом раунде цикла (не один раз до цикла) и передаёт её в
     `api.tools(location_id)` — чтобы после будущих `move`-тулов фильтр не
     отставал от факта.
  3. В `SYSTEM`-промпт добавлена одна статическая строка-подсказка:
     "используй `get_seller_stock`, не `get_inventory`, чтобы узнать, что
     продаёт NPC" — прямое исправление класса ошибки из `#ENG-012`, ценой
     в токены один раз на весь диалог, а не на каждый раунд.
- Покрыто тестом `test_tools_filtered_by_location`.

## #ENG-014 — Discovery-паттерн (`help` → категории → тулы) отклонён для текущего масштаба
- Дата: 2026-09-28

## #ENG-018 — Внешние пресеты механик и защита ActionAPI от ошибок аргументов
- Дата: 2026-09-29
- Кем: совместно
- Статус: Реализовано
- Проблема: параметры базовых механик начинают протекать в код движка.
  В частности, `advance_time()` был жёстко привязан к 24-часовым суткам и
  строковому разбору времени. Одновременно некорректный tool call от LLM
  без обязательного аргумента мог уронить REPL через `KeyError`.
- Решение:
  1. Параметры календарного времени вынесены из `WorldEngine` во внешний
     JSON-пресет `data/rules/presets/<id>.json`.
  2. World pack указывает `rules_preset`; Engine загружает пресет как
     конфигурацию механики, а не как часть лора. Сейчас пресет описывает
     базовые единицы календаря: минут в часе, часов в сутках, дней в месяце
     и месяцев в году.
  3. Конкретный мир может использовать один из готовых пресетов; генератор
     мира или ручной автор в будущем может выбрать/создать свой. Генерация
     по seed не является обязательной частью этой системы.
  4. `ActionAPI.call()` не обращается к обязательным аргументам через
     `args['...']` до проверки их наличия: отсутствующий аргумент
     возвращается как структурированная ошибка `ok:false`, а не исключение.
- Граница: пока реализована только календарная механика. Другие механики
  не превращаются автоматически в конфигурационные поля до появления
  реального требования; не создаём универсальный огромный rules-файл.

## #ENG-019 — Contextual tool surface and reusable allow_to mechanism
- Дата: 2026-09-29
- Статус: Реализовано
- Проблема: LLM приходилось передавать внутренние ID и лишние аргументы
  для обычных взаимодействий (например, seller_id в каждом вызове
  торговли). Чем сложнее один tool call, тем больше точек, где небольшая
  модель может ошибиться.
- Решение:
  1. Tools проектируются как маленькие примитивы с минимальным числом
     аргументов; Engine сам подставляет известный контекст.
  2. Добавлен переиспользуемый механизм allow_to у сущностей:
     data.allow_to содержит действия, которые сущность может выполнять
     в текущей модели мира. Для текущего vertical slice используется
     "trade"; позже тот же механизм может применяться к другим
     взаимодействиям.
  3. Торговля стала контекстной сессией. В обычном режиме LLM видит
     start_trade; Engine находит доступных NPC в текущей локации.
     Если торговцев несколько, Engine возвращает нумерованный список, а
     LLM выбирает номер. После выбора LLM видит только get, buy, end и не
     передаёт seller_id.
  4. Внутренние Engine-методы get_seller_stock и buy_item остаются
     детерминированными примитивами механики, но больше не являются частью
     обычной LLM-facing tool surface.
  5. Контекстная tool surface переиспользуется как общий механизм для
     будущих режимов взаимодействия, а не только для торговли.
- Граница: сложная система расписаний/временной доступности NPC пока не
  реализуется. allow_to сейчас является статическим world-data
  capability; динамические условия добавляются отдельно, когда появится
  реальное требование.

## #ENG-020 — Изменения состояния мира атомарны
- Дата: 2026-09-30
- Кем: ИИ (аудит кода по запросу пользователя, реализация — ИИ)
- Статус: Реализовано
- Проблема: `Database.execute()` коммитил каждый запрос отдельно, поэтому любая
  мутация из нескольких запросов могла остановиться посередине. Воспроизведено
  в тестах: `upgrade_stat` при сбое второго запроса уже повысил стат, но не
  списал деньги; `buy_item` мог списать деньги, не выдав предмет; падение
  `load_world` посреди вставки оставляло `world_state` и часть сущностей, а
  повторный запуск считал мир загруженным и не догружал остальное (нужно было
  вручную удалять `world.db`). Для движка, чья главная идея — «БД это
  единственный источник истины», это главный риск целостности.
- Решение: `Database.transaction()` — контекстный менеджер «всё или ничего».
  Вложенный блок присоединяется к внешнему. `execute()` вне транзакции
  по-прежнему коммитит сразу. `load_world`, `buy_item`, `upgrade_stat`,
  `advance_time` выполняют все записи внутри одной транзакции.
- Правило на будущее: любая новая мутация, которая пишет больше одной записи,
  обязана быть обёрнута в `with self.db.transaction():`.
- Проверка: `tests/test_transactions.py`, `tests/test_loader.py` (инъекция сбоя
  через фикстуру `fail_on`).

## #ENG-021 — `rules_preset` применяется при каждой загрузке мира
- Дата: 2026-09-30
- Кем: ИИ
- Статус: Реализовано (уточняет #ENG-018)
- Проблема: `load_world()` выходил, как только находил `world_state` в БД, до
  загрузки `rules_preset`. Первый запуск мира работал по пресету, а после
  перезапуска тот же сохранённый мир молча жил по дефолтным правилам
  (воспроизведено: `hours_per_day` 30 → 24).
- Решение: правила механик — конфигурация мира, а не сохранённое состояние.
  `load_world()` теперь всегда читает и валидирует `world.json` и применяет
  `rules_preset`, а состояние создаёт только в пустой БД. Возвращает `True`
  (создано) / `False` (мир уже был).
- Следствия: (1) битый `world.json` блокирует и загрузку существующего
  сохранения; (2) правка пресета меняет поведение уже идущих игр — для
  календаря это может дать странные, но не повреждённые даты; если понадобится
  «заморозить» правила на момент создания мира, это отдельное решение
  (запись id/копии пресета в БД).
- Валидация: `rules_preset` — только простой id (`[A-Za-z0-9_-]+`), это имя
  файла, а не путь (защита от `../` для сторонних world packs). Заодно
  ужесточена валидация `world.json`: id/type/name — непустые строки, `data` и
  `stats` — объекты, `starting_money` — целое (bool не считается).

## #ENG-022 — `ActionAPI.call()` не бросает исключений
- Дата: 2026-09-30
- Кем: ИИ
- Статус: Реализовано (закрывает оставшуюся часть #ENG-018)
- Проблема: #ENG-018 закрыл `KeyError` на отсутствующих аргументах, но
  неверный *тип* по-прежнему ронял REPL (`advance_time` с `"abc"` → `ValueError`
  в `int()`), а `True` принимался как число 1. `get_entity` для неизвестного
  id отдавал `null`, и модель должна была гадать, что это значит.
- Решение: `call()` — единственная точка входа с контрактом «не бросает».
  Аргументы проверяются по типу (`_as_int`, `_text`); числа строкой (`"30"`)
  и `30.0` принимаются, потому что слабые модели так пишут, `bool` — нет.
  Неверные аргументы → структурированный `{'ok': False, 'error': ...}`.
  Неожиданное исключение внутри Engine логируется (`logging`, с traceback) и
  возвращается модели как `INTERNAL_ERROR`; благодаря #ENG-020 мир после
  такого сбоя остаётся согласованным. `get_entity` для неизвестного id →
  `ENTITY_NOT_FOUND`.
- Граница: формат ответов остаётся разнородным (список / объект / `ok:false`),
  единый конверт `{ok, data|error}` пока не вводился — это отдельное решение,
  потому что меняет то, что видит модель.

## #ENG-027 — Взаимодействие прерывает другие; политика режимов
- Дата: 2026-10-01
- Кем: пользователь (принцип: взаимодействие прерывает другие, `act` прикрывает
  забытый `end`), ИИ (анализ живого лога, реализация)
- Статус: Реализовано. Уточняет #ENG-019, п.3
- Проблема: в живой сессии игрок попрощался с торговцем, а модель не вызвала
  `end`. Режим торговли остался, список тулов сузился до `get/buy/end`, и на
  просьбу повысить характеристику модель выдумала консоль с «отказом доступа».
  То есть дрейф канона создал сам движок: выход из режима зависел от того,
  вспомнит ли слабая модель вызвать `end`. Менять модель не лечение: правило
  режимов должно держаться в движке.
- Решение:
  1. Взаимодействие прерывает другие: нельзя торговать с тем, от кого ушёл.
  2. Каждый тул имеет вид: `read` (смотрит), `act` (меняет мир), `enter`
     (начинает взаимодействие), `inside` (существует только внутри него).
  3. Что делать с `read` и `act` во время взаимодействия, описывают данные:
     `MODE_POLICY` в `engine/actions.py`. Значения `allow` (разрешено),
     `end` (разрешено, успешный вызов завершает взаимодействие), `block`
     (тул скрыт, вызов даёт `BLOCKED_BY_INTERACTION` со списком доступного).
  4. Торговля: `read` — `allow`, `act` — `end`. Успешный `act` завершает
     торговлю, результат помечается `interaction_ended`. Ошибочный вызов
     (мусор от модели, нет такого стата) торговлю не завершает.
  5. Бой (на будущее): `read` — `allow`, `act` — `block`. Проверено тестом через
     подмену политики, самого боя нет.
  6. Режим без записи в `MODE_POLICY` закрыт целиком (fail closed): ошибка
     конфигурации не должна молча разрешать действия.
  7. `end` остаётся явным выходом из торговли.
- Граница: политика пока константа в коде, а не данные мира или пресет;
  положение в пространстве не моделируется (нет `move`), «ушёл» здесь означает
  «занялся другим действием».
- Связь с курсом: это минимальная часть автомата состояний из
  `ideas/INTENT_PARSER_IDEA.md` (состояние определяет допустимые действия).
- Проверка: `tests/test_interactions.py`, включая регрессию по живому логу.

## #ENG-028 — Упрощённая tool surface: одно слово, не больше одного аргумента
- Дата: 2026-10-01
- Кем: пользователь (принцип: названия и использование тулов максимально
  простые; недостатки решать в движке, а не списывать на слабость модели),
  ИИ (конкретные имена, реализация)
- Статус: Реализовано. Уточняет #ENG-013 и #ENG-019, п.1
- Проблема: тулы вроде `get_location_contents(location_id)`,
  `upgrade_stat(player_id, stat)`, `search_entities(query, type, location_id)`,
  `get_inventory(owner_id)` требовали внутренних id и нескольких аргументов;
  имена `get` и `end` ничего не говорили сами по себе; в живом логе модель
  показывала игроку названия команд.
- Решение:
  ```text
  было                                         стало
  get_world_state + get_location_contents(id)  look()
  get_entity(entity_id)                        inspect(id?)   без id: сам игрок
  search_entities(query, type, location_id)    find(query)
  get_inventory(owner_id)                      inventory()    только своё
  upgrade_stat(player_id, stat)                upgrade(stat)
  advance_time(minutes)                        wait(minutes)
  start_trade(choice?)                         trade(choice?)
  get / buy / end                              stock / buy / end
  ```
  Правила: имя — одно короткое слово (`[a-z]{2,10}`); не больше одного
  аргумента; внутренние id модель не передаёт (id игрока движок берёт из мира,
  `WorldEngine.player_id()`, а не из константы); все ответы — объекты;
  `stock` отдаёт номер, имя и цену без внутренних id; ошибки подсказывают
  допустимое (`UNKNOWN_STAT` → список статов, `TOOL_NOT_AVAILABLE` → что доступно).
  Тулы описаны в `ActionAPI.registry` (схема, вид и обработчик рядом): новый
  тул добавляется в одном месте вместо двух.
- Совместимость (правило 11): старые имена не поддерживаются (`UNKNOWN_TOOL`).
  Ломать пока нечего: сырые сообщения LLM и вызовы нигде не сохраняются
  (#ENG-003). Когда появится журнал вызовов, имена тулов станут частью формата
  и менять их можно только с версией.
- Попутно (правило 4, детерминизм): у `get_seller_stock`, `inventory` и
  `get_location_contents` задан полный порядок (`ORDER BY`), потому что номера
  `choice` строятся из этих списков, а четыре «Стула» в таверне различались
  только по id.
- Проверка: `tests/test_actions.py`, `tests/test_interactions.py`; сторожевые
  тесты проверяют, что имена — одно слово и у тула не больше одного аргумента.
