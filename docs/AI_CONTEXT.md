# AI_CONTEXT.md — читать первым

Этот файл — точка входа для любой LLM (Claude, GPT, локальная модель и т.д.),
которая начинает или продолжает работу над этим проектом. Автор проекта
курирует разработку и почти не пишет код сам — весь код пишет ИИ. Поэтому
этот файл и три соседних документа (`ARCHITECTURE.md`, `PROJECT_STRUCTURE.md`,
`DECISIONS.md`) — это твоя единственная память о проекте между сессиями.

## Как этим пользоваться (для ИИ)

1. Прочитай этот файл целиком.
2. Прочитай `DECISIONS.md` — там зафиксировано, что и почему уже решено.
   Не предлагай заново то, что там уже отвергнуто.
3. Прочитай `PROJECT_STRUCTURE.md` — актуальная карта файлов и папок.
4. Прочитай `ARCHITECTURE.md` — принципы, которые нельзя нарушать при
   написании кода.
5. Если чего-то не хватает в этих файлах для выполнения задачи — **спроси
   у пользователя**, не додумывай молча.
6. В конце сессии, если было принято архитектурное решение или добавлена
   значимая фича — допиши запись в `DECISIONS.md` и обнови
   `PROJECT_STRUCTURE.md`, если менялась структура файлов.

## Как этим пользоваться (для человека)

В начале новой сессии с любым ИИ — скидывай эти 4 файла (или весь `docs/`)
первым сообщением, до постановки задачи. Это заменяет ручной пересказ
статуса проекта, который раньше делался вручную (как было в первом
handoff-документе 27–28 сентября 2026).

## Проект одной строкой

**ALLIZIUM Engine** — движок для long-form текстовых RPG с локальной LLM
в роли NPC-мозга и рассказчика, рассчитанный на тысячи ходов без потери
контекста и без дрейфа канона. Пишется так, чтобы движок можно было
опубликовать как opensource-платформу для модинга — не "игра для себя",
а фреймворк, на котором сторонние люди смогут собирать свои миры.

## Главный принцип проекта (не нарушать никогда)

> **Engine знает, что существует. LLM решает, что делать и как это описать.**
> **PLAYER CLAIM ≠ CANON.**

Источник истины — SQLite через `engine/`. LLM никогда не меняет состояние
мира напрямую — только через tool calls, которые обрабатывает `ActionAPI`.
LLM не должна быть базой данных мира.

## Второй главный принцип (актуален с 28.09.2026)

> **Engine не должен знать ни про один конкретный мир.**

Ядро (`engine/`) обязано оставаться world-agnostic: никаких имён NPC,
локаций, предметов, названий валюты и т.п. в коде движка. Весь лор —
данные, а не код. Подробности — в `ARCHITECTURE.md` и `MODDING.md`.
Это решение принято, но **на 28.09.2026 ещё не реализовано полностью** —
смотри `DECISIONS.md` и открытые задачи в `PROJECT_STRUCTURE.md`.

## Текущий статус (обновляется по ходу проекта)

- Рабочий вертикальный срез на Python 3.14.5 + Ollama + Gemma (модель
  сейчас `gemma4:e4b`) — main.py, tool-calling loop, SQLite как источник
  истины. Работает: покупка предмета, апгрейд стата, проверка "игрок не
  может выдумать несуществующий предмет".
- Закрыто 28.09.2026: tool-call loop теперь многораундовый (`#ENG-002`),
  есть обработка ошибок связи с Ollama (`#ENG-002b`), убран дефолт
  `seller_id='boris'` (`#ENG-004a`), исправлен баг с `get_inventory`
  вместо `get_seller_stock` (`#ENG-012`), тулы фильтруются по локации +
  шпаргалка в system prompt (`#ENG-013`). Discovery/`help`-паттерн для
  выбора тулов осознанно отложен (`#ENG-014`, не запрещён навсегда).
- Известные незакрытые технические долги (см. `DECISIONS.md`):
  - `#ENG-003` — нет персистентности диалога между запусками (только
    `events` в БД, сырые сообщения LLM нигде не сохраняются); нет
    суммаризации.
  - `#ENG-004` — мир (`seed_demo_world`) всё ещё зашит в Python-коде
    `engine/world.py`, а не вынесен в `data/worlds/<name>/world.json` —
    рефакторинг запланирован, не сделан (убрать дефолт `seller_id`
    — сделано, полный вынос сущностей в данные — нет).
  - `#ENG-011` — манифест/lock-файл модов и генератор диаграмм
    спроектированы, генератор не написан.
- Железо: три ПК (RTX 2060 Super 8GB, RTX 4060 8GB, RTX 5060 16GB).
  Основная модель гоняется на самом мощном ПК, движок разрабатывается на
  слабом.

## Жёсткие правила для любого кода, который пишет ИИ в этом проекте

- SOLID и модульность — код в `engine/` не должен знать о конкретном
  сеттинге, персонаже или предмете. Если тест на это нужен — тестовые
  данные лежат в `data/worlds/`, не в самом модуле.
- Любое изменение, влияющее на архитектуру (новая таблица, новый слой,
  смена формата хранения) — сначала запись в `DECISIONS.md`, потом код.
- Код рассчитан на то, что его будет читать и дописывать **другая** ИИ
  в другой сессии, без общего с тобой контекста разговора. Пиши так,
  будто объясняешь незнакомому разработчику, а не текущему собеседнику.
- Проект задуман как open-source / moddable — не добавляй ничего, что
  жёстко завязано на личные предпочтения текущего мира ALLIZIUM, если
  это можно вынести в конфиг/данные.
