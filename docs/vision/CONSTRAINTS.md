# Ограничения: слои, область, происхождение, коэволюция

Объединяет три заметки из брейнштурма 2026-10-01. Это идея и обсуждение, не
итоговый API. Принятое попадает в `../DECISIONS.md`.

## Ограничение это часть модели реальности

Не защитный `if` вокруг движка, а то, что определяет пространство допустимых
конструкций. Возможности задают, что можно построить, ограничения задают, что из
построенного допустимо.

## Три слоя

| Слой | Вопрос | Примеры |
|---|---|---|
| Core | что значит быть корректной конструкцией внутри движка | у сущности есть идентичность; ссылки на несуществующее не валидны; транзакция атомарна; событие соответствует контракту |
| Module | какие законы действуют в области модуля | химия: валентность, правила реакции; физика: сохранение величин |
| World / Mod | какие дополнительные законы в этой реальности | воскрешение разрешено или запрещено; телепорт в королевстве A запрещён |

Core не знает доменных законов (никакой химии, магии, RPG-классов). Модуль
регистрирует свои ограничения, движок их проверяет:

```text
Module → provides constraints → Engine validates
```

**Граница полномочий:** модуль может расширять пространство ограничений, но не
отменять фундаментальные инварианты ядра. «Сущность без ID» невалидно;
«у свойства electron_state есть дополнительные ограничения» нормально.

## Область, происхождение, приоритет

У ограничения четыре независимых характеристики:

| Характеристика | Что это |
|---|---|
| существование | само правило |
| область действия | `Core → Module → World → Region → Entity → Action` |
| приоритет | как разрешается конфликт нескольких ограничений |
| происхождение | откуда правило: `core`, `module: chemistry`, `world: fantasy_01`, `entity: sword_17` |

Проверка действия: собрать применимые ограничения → проверить → при конфликте
разрешить → ACCEPT или REJECT.

**Приоритет сознательно не фиксируется**, пока не появятся реальные конфликты.
Сначала определить уровни и контракт ограничения, затем проверить на случаях:
Core+Module, Module+Module, Module+World, World+Region, Region+Entity, несколько
независимых модулей, несовместимые ограничения. Только после этого закреплять
механику.

## Формат отказа (кандидат в контракт)

```text
REJECTED
  constraint: chemistry.valence_limit
  scope:      molecule_42
  reason:     requested bond is invalid
  source:     Chemistry Module v0.3
```

Голое «INVALID» запрещено (`GOLDEN_RULES.md`, правило 5). Отказ нужен и ИИ, и
новичку как обратная связь.

## Коэволюция возможностей и ограничений

```text
примитивы → новые возможности → новые комбинации → новые конструкции
          → новые ограничения и допустимые состояния → ...
```

Ограничение не вечно: «A→B невозможно» может стать «A+X→B возможно» после появления
нового примитива, и наоборот, более точная модель находит новые ограничения.
Поэтому важно определить **как** ограничения существуют, регистрируются,
применяются, объясняются и эволюционируют, а не перечислять их заранее.

Следствие: ядро не спрашивает «ты построил то, что мы ожидали?», оно спрашивает
«это допустимая конструкция по активным законам этой реальности?». Свобода
дизайна отделена от валидности симуляции.
