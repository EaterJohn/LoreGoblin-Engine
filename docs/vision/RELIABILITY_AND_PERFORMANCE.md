## Производительность

Огромное пространство свойств не «вычисляется бесконечно»: его не считают целиком.
Нагрузку определяют три вещи:

1. **Сколько сущностей сейчас разрешено в детали.** При разрешении по требованию и
   агрегатах стоимость растёт с активностью игрока, а не с размером мира. Постоянно
   хранится только ставшее каноном.
2. **Стоимость шага.** Событийное обновление вместо перебора всех сущностей каждый тик.
   Риск: перебор «правила × сущности» на каждое событие; нужны индексы правил по
   тегам и триггерам.
3. **LLM.** Вызов локальной модели занимает секунды; движок на Python и SQLite на
   этом фоне почти бесплатен. Узкое место скорее в генерации текста.

Реальные риски: рост лога событий (снимки, политика хранения), JSON-компоненты в
SQLite при частых запросах по свойствам (индексы, кэш), разгон детали (каждая
материализация тянет следующую; нужны бюджеты и лимит глубины).

**Предложение:** до оптимизации задать бюджеты (например, «действие игрока в мире на
N тысяч сущностей не дольше X мс на движке») и добавить в набор приёмки
синтетический мир для замера. Оптимизировать по измерениям, а не по догадкам. N и X
решает владелец проекта.

## Структура репозитория и ветки

- **Один репозиторий, жёсткая иерархия в структуре** (например `engine/core/`,
  `engine/...`, `mods/<имя>/`). Направление зависимостей («Core не зависит от
  модулей и LLM») проверяет CI, например `import-linter`, чтобы правило из
  `PRINCIPLES.md` стало автоматической проверкой. Базовый CI (pytest, ruff, mypy)
  уже в плане: `../ideas/IDEAS_INDEX.md`, порядок, пункт 6.
- **Ветки короткоживущие:** `main` стабильная, фича-ветки на задачу (как
  `feature/world-loader`, `hardening/atomic-state`). Долгоживущие ветки «только ядро»
  и «только модули» не вести: они расходятся, слияние становится мучительным.
- **Версии и теги ядра.** Когда контракт ядра стабилизируется (API, схема манифеста),
  модули можно выносить в отдельные репозитории, привязанные через `requires_engine`.
  Раньше этого момента раздельные репозитории только добавляют проблем.
- `CODEOWNERS` и защита `main` (обязательные проверки), когда появятся другие участники.
