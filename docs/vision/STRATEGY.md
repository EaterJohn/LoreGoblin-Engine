# Стратегия: от симулятора миров к основе симуляций

Решение владельца 2026-10-01, зафиксировано в #ENG-024. Объединяет три
брейнштурм-документа (смена курса, тезис про инфраструктуру ИИ, метафора «точка»).

## Что изменилось

Старая цель: детерминированная реалистичная тёмно-фентезийная RPG с LLM без
выдуманного канона. Один такой продукт требует физики, химии, биологии, когниции,
экономики, пространства, времени и ещё десятка областей, и вся эта работа
оказывается спрятана внутри одной игры. Эффективнее построить механизм один раз,
а игры и другие симуляции собирать поверх него.

```text
было:  LLM RPG → живой мир → симулятор миров → VR-клиент
стало: примитивы → контракты → модули → основа симуляций → настраиваемые реальности
```

RPG остаётся, но в роли **эталонного мира и стенда**: он не даёт абстракциям
оторваться от реальных требований. Он не цель проекта.

## Миссия

Создать экосистему, в которой ИИ строит, комбинирует, проверяет и запускает
симуляции из независимых модулей. Симуляция может быть игровым миром,
лабораторией, экономикой, экосистемой или вымышленной вселенной.

**Не строить мир. Строить механизм, которым строят миры.**

## Что продаёт проект: слой доверия

Сильный ответ на вопрос «почему ИИ не пишет просто Python с SciPy»: не потому что
наша физика лучше. Потому что у нас есть то, чего нет в голом коде:

- единые контракты между модулями (единицы, время, идентичность);
- проверка до фиксации и объяснимый отказ (`GOLDEN_RULES.md`, 3 и 5);
- происхождение каждого факта (какое правило, какой модуль);
- воспроизводимость и откат (`TRUST_AND_ROLLBACK.md`);
- интерфейс, рассчитанный на LLM.

Схема: LLM предлагает, ядро проверяет, модуль считает, ядро фиксирует, LLM
объясняет результат. Это обобщение #ENG-001.

## Критерий успеха

> ИИ с помощью LoreGoblin строит симуляцию, под которую LoreGoblin специально
> не проектировался, и ядро для этого не правится.

Если «все играют в LoreGoblin» не случилось, архитектура всё равно оправдана,
если выполняется критерий выше. Для автора движок нужен сам по себе, и это
главная защита от провала по причине отсутствия аудитории.

## Вехи вместо «точки и взрыва»

Метафора «в начале была точка, потом взрыв» остаётся горизонтом: из минимальных
примитивов и законов собирается сложное. Планом она быть не может, у неё нет
условия остановки (каждая ступень материя → звёзды → химия → жизнь отдельная
наука). Поэтому план измеряется вехами (порядок важен: M0 раньше инфраструктуры, она строится по мере появления второго потребителя):

| Веха | Условие выполнения |
|---|---|
| M0 | Играбельный RPG-мир на текущем срезе: тысячи ходов без дрейфа канона, сохраняемый диалог, проверка нарратива. Без него остальное теория |
| M1 | Физический модуль (минимальный, с аналитическими эталонами) подключён через контракт ядра |
| M2 | Второй домен вне RPG собран без правок ядра |
| M3 | ИИ добавляет третий модуль через конвейер проверки, и конвейер отклоняет заведомо неверный |
| M4 | Реестр модулей открыт для сторонних авторов (git-репозиторий с индексом по тегам) |

Реальность как конфигурация (законы, константы, термодинамика, время) это
следствие модульности, а не отдельный проект. Конфигурация выбирается
пользователем, ядро проверяет её внутреннюю согласованность по контрактам.

## Чего проект не делает

- Не обещает «симуляцию всей реальности». Это горизонт.
- Не пишет всю физику и химию сам: модули появляются по вехам и по потребности.
- Не считает детерминизм доказательством корректности (`TRUST_AND_ROLLBACK.md`).
- Не требует хостинга и платформы: протокол и реестр отделены от сервисов.

## Риски

1. **Обобщение без второго потребителя** это догадка о форме. Лечит веха M2.
2. **Сложность переезжает в модули.** Композиция физики и химии требует единых
   единиц, шага времени, законов сохранения: это урок ROS, нужен контракт.
3. **Детерминированная выдуманная физика** опаснее галлюцинации, потому что
   выглядит авторитетно. Нужны независимые эталоны и песочница.
4. **Раздутое ядро.** Если Constraint, Space, Resolution, Time все в ядре, оно
   перестаёт быть маленьким (`KERNEL_AND_SUBSYSTEMS.md`).
5. **Реальные риски соло-проекта:** объём работы и один автор, а не деньги и
   хостинг, как у большинства предшественников (`PRECEDENTS.md`).
6. **Приток новичков** создаст поток слабых модулей. Воронка вкладов должна
   пропускать любого, но через карантин и эталоны (`MODULE_CONTRACT.md`).
7. **Железо:** локальные модели 8–16 ГБ плохо генерируют модули. Ценность в
   конвейере проверки, а не в генераторе.

## Что НЕ меняется

Принципы `PRINCIPLES.md`, `ENG-001`, `ENG-004`, `ENG-020`, `ENG-022`, ActionAPI,
канон против LLM. Это фундамент, на котором строится новая цель.
